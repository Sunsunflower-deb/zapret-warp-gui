# Измерения: что реально блокируется и какая техника работает

Замеры сделаны на живой сети за машиной разработчика — это не синтетика и не
лаборатория. Заполнено по протоколу из плана (§7.3, задача 0.3).

**Условия:** 2026-11-25, Windows, права обычные (без администратора), поэтому
`winws.exe` (у него в манифесте `requireAdministrator`) запустить нельзя.
Значит десинк мерился **не через winws**, а эмуляцией на уровне сокетов:
ClientHello собирается через `ssl.MemoryBIO` и отправляется двумя кусками —
это ровно то, что делает `multisplit`. Режимы, которым нужен уровень пакетов
(`fake`, `fooling`, `disorder`), так проверить нельзя.

**Состояние WARP в момент замеров:** подключён (`Status update: Connected`,
`Network: healthy`), режим `warp+doh`, протокол MASQUE (HTTP/3 с фолбэком на h2),
exclude-список по умолчанию. То есть десинк в этих замерах не участвовал вообще.

## 1. Базовая линия: что не открывается без всякого десинка

3 попытки на хост, таймаут 4 с, TLS-рукопожатие без проверки сертификата.

| Хост | Успех | Медиана | Класс |
|---|---|---|---|
| `cloudflareclient.com` (WARP) | 3/3 | 146 мс | ok |
| `discord.com` | 3/3 | 170 мс | ok |
| `www.twitch.tv` | 3/3 | 176 мс | ok |
| `x.com` | 3/3 | 158 мс | ok |
| `www.instagram.com` | 3/3 | 207 мс | ok |
| `www.google.com` | 3/3 | 234 мс | ok |
| `www.facebook.com` | 3/3 | 249 мс | ok |
| **`www.youtube.com`** | **0/3** | — | `timeout` |
| **`api.telegram.org`** | **0/3** | — | `timeout` |

Итого 21/27. DNS не подменяется: ответы системного резолвера совпадают с
DNS-over-HTTPS (Cloudflare) для `api.telegram.org`, `www.youtube.com`,
`discord.com`, `cloudflareclient.com`.

Вывод: фильтр есть, но узкий — YouTube и Telegram. WARP-endpoint при этом
доступен без десинка, то есть **для поднятия самого туннеля на этой сети десинк
не нужен**.

## 2. Уровень блокировки: SNI или IP?

Ключевой опыт — один и тот же IP, разные SNI:

| Что подключаем | TCP | TLS |
|---|---|---|
| IP YouTube + SNI `www.youtube.com` | ok, 71 мс | **timeout** |
| IP YouTube + SNI `www.google.com` | ok | **ok, 8/8, 350 мс** |
| IP Telegram `149.154.166.110` | **timeout** | — |
| IP Discord (контроль) | ok, 45 мс | ok, 131 мс |

Отсюда:

* **YouTube блокируется по SNI.** Один и тот же сервер с «разрешённым» SNI
  отвечает 8/8. Значит это ровно тот случай, где десинк помогает.
* **Telegram блокируется по IP** (TCP до IP не устанавливается). Десинк тут
  бесполезен в принципе — нужен туннель с площадкой, откуда этот IP доступен.
  WARP на этой сети выходит через `colo DME` (Москва) и не помогает: блокировка
  действует и там.

## 3. Насколько рано надо резать ClientHello

Размер ClientHello — 517 байт, поле SNI `www.youtube.com` занимает байты
127–141. Отправляем двумя сегментами с паузой 4 мс, 4 раунда на позицию,
позиции чередуются по кругу.

| Позиция разреза | Успех |
|---|---|
| 1 (в заголовке записи) | 3/4 |
| 3 | **4/4** |
| 10 | 1/4 |
| 50 | 0/4 |
| 100 | 0/4 |
| 120 | 1/4 |
| 126 (перед SNI) | 0/4 |
| 127 (начало SNI) | 1/4 |
| 134 (середина SNI) | 0/4 |
| 142 (конец SNI) | 1/4 |
| без разреза | 0/4 |

Отдельный прогон с 8 раундами и контролем:

| Техника | Успех | Медиана |
|---|---|---|
| без разреза | 2/8 | 1163 мс |
| разрез в 1-м байте | **8/8** | 230 мс |
| разрез по середине SNI | 0/8 | — |
| разрез сразу после SNI-хоста | 2/8 | 298 мс |

**Граница между 3 и 10 байтами.** Пока первый сегмент слишком короткий, чтобы
быть началом TLS-записи, DPI не разбирает поток: он видит 1–5 байт и теряет
интерес. Как только первый сегмент похож на TLS (`0x16 0x03 …` и далее), DPI
дожидается продолжения, собирает SNI и рвёт соединение — поэтому разрезы
≥10 байт, а также «по середине SNI» и «после SNI» не работают.

Практический вывод: **резать надо в 1–3-м байте** — это ровно
`--dpi-desync-split-pos=1`, а не `midsld` и не `sniext+1`.

## 4. Что из этого следует для стратегий

| Техника | Ожидание на этой сети | Основание |
|---|---|---|
| `multisplit` + `split-pos=1` | работает | 8/8 при разрезе в 1-м байте |
| `midsld`, `sniext+1`, `endhost-2` | не работает | 0/8 при разрезе от 10-го байта и в поле SNI |
| `fake` (первый сегмент — чужой CH) | вероятно работает | не проверено: нужен уровень пакетов |
| `fake,multisplit` + `split-pos=1` | должно работать | покрывает оба типа DPI: короткий первый сегмент + фейк |

Поэтому в 1.3.1:

* `strategies/warp_simple_fake.bat` → `--dpi-desync=fake,multisplit` +
  `--dpi-desync-split-pos=1`;
* в автоподборе появились кандидаты `split1` и `fake-split1` (всего 20).

Стратегии из апстрима, у которых первый сегмент тоже не похож на TLS
(`--dpi-desync-split-pos=1`): `general.bat`, `general_alt6`, `general_alt11`,
`general_alt12`, `general_fake_tls_auto`, `general_fake_tls_auto_alt`,
`general_fake_tls_auto_alt2`, `general_fake_tls_auto_alt3`.

## 5. Что НЕ проверено

* **Реальный прогон winws** — нет прав администратора (WinError 740). Всё
  измеренное выше получено без десинка как такового: это поведение сети, а не
  поведение стратегии в сборе.
* **`fake`, `fooling`, `disorder`, `hostfakesplit`** — требуют уровня пакетов
  (TTL, внеочередная отправка), из Python без администратора недоступны.
* **Telegram через WARP с другим `colo`** — не проверялось; вывод «не поможет»
  основан на том, что текущий выход (`DME`) не помогает, а десинк тут ни при чём.
* Комбинация «WARP выключен + только десинк» — не мерилась: без winws нечего
  включать.

## 6. Как повторить

```bat
:: с правами администратора, на этой же сети
zapret-warp-cli.exe tune --apply
zapret-warp-cli.exe check
```

Для ручной проверки без десинка (как в §1–3) достаточно `python cli.py check`:
он покажет те же классы ошибок и внешний IP.
